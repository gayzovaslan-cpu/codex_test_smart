# Инструкции для работы с проектом

## Цель и источники

- Проект посвящён Kaggle NeurIPS 2026 Smart Buildings: одна HVAC-политика должна переноситься на новые здания и климатические условия.
- Перед исследованием или разработкой прочитай релевантные разделы `RL_STRATEGY.md`. Рекомендации алгоритмов в нём — проверяемые гипотезы, а не обязательный выбор навсегда.
- Основной внешний источник — официальный starter kit: https://github.com/smart-buildings-2026/starter-kit. Правила Kaggle, актуальный код среды и scorer имеют приоритет над предположениями и устаревшими описаниями. При расхождениях указывай источник и версию.
- Состояние на момент создания этого файла: в репозитории есть аналитический отчёт; starter kit, обучение и тесты ещё не добавлены. Перед запуском команд проверяй фактическое содержимое проекта. Команды из отчёта относятся к каталогу starter kit.

## Контракт среды

- Это централизованное управление зданием с гибридными действиями. Для `K` AHU и `V` зон ожидаются `discrete_action: int32[K+1]` со значениями `{0,1}` и `continuous_action: float32[3K+2+2V]` в `[-1,1]`. Сверяй контракт с используемой версией среды.
- Получай размеры, индексы наблюдений и действий, соответствие зон AHU и нормализацию из `building_meta_data` и `action_spec`. Поддерживай разное число зон и AHU; не привязывай policy к фиксированным смещениям или конкретному публичному зданию.
- Ноль непрерывного действия означает середину диапазона. Учитывай вентиляционные floors, ограничения рециркуляции и различие между охлаждением AHU и догревом VAV/HWS.
- Возвращай массивы правильной формы и dtype, конечные значения в допустимых границах. Сбрасывай историю и recurrent state на новом сценарии.
- Actor при inference использует только доступные наблюдения, metadata и собственную причинную историю. Не передавай ему training-only признаки, истинную будущую погоду или идентификаторы закрытых сценариев.

## Разработка и проверки

- Начинай с простого работающего контроллера и совместимого интерфейса. Усложнение архитектуры обосновывай отдельными экспериментами.
- Используй совместимые зависимости из выбранной версии starter kit; не обновляй отдельные пакеты без проверки их ограничений совместимости.
- При изменении кода выполняй подходящие существующие проверки. Для policy проверяй формы, границы и корректность индексов на зданиях разных размеров, затем запускай функциональный rollout.
- Перед длительным обучением измеряй время шага симулятора, потребление ресурсов и ожидаемый бюджет. Выбирай параллелизм по доступным ресурсам и сохраняй возобновляемые checkpoints.
- Различай суточный smoke test и полную оценку: текущий полный эпизод — 8 640 шагов по 5 минут, без бесплатного warm-up. Не сравнивай returns разных горизонтов.
- При изменении интерфейса policy проверяй локальный evaluator и Kaggle submission adapter отдельно. Локальный обычный класс и подкласс gateway `Policy` имеют разные требования интеграции.

## Эксперименты и метрика

- Основной критерий — исходный score организаторов: среднее по сценариям от `abs(total_reward / 8640)`, меньше лучше. При текущей неположительной reward это эквивалентно максимизации среднего недисконтированного return. Сценарии равновзвешены; baselines не входят в формулу score.
- Текущая reward плотная: комфорт, энергия и углерод с весами `0.6 / 0.2 / 0.2`. Она не ограничена диапазоном `[-1,0]`. Не скрывай большие comfort failures обрезанием исходной метрики.
- Reward shaping оценивай по неизменённой официальной reward. Явно описывай отличие training objective от leaderboard objective.
- Делай validation по целым зданиям и климатам. Не смешивай соседние переходы одного rollout между train и validation; validation не должен попадать в replay, подгонку нормализации или подбор teacher.
- Сравнивай с `pid_water` и другими опубликованными baselines на одинаковых сценариях и горизонте. Отдельно указывай число env transitions, wall time и seeds обучения.
- Для каждого эксперимента сохраняй версию кода и среды, конфигурацию, seed, split сценариев, горизонт, checkpoint и исходные результаты. Не смешивай устаревшие results с новым запуском.

## Отчётность и Git

- Общайся с пользователем по-русски; сохраняй принятые в коде имена API и алгоритмов.
- Разделяй подтверждённые факты, предложения и измеренные результаты. Не выдавай опубликованные baseline returns за собственные rollout и не описывай непроведённые проверки как успешные.
- В итоговом сообщении указывай, что изменилось, что проверено и какие ограничения остались. Отдельно отмечай состояние Git: локальные изменения, созданный коммит и выполненный push — разные результаты.
- Сохраняй пользовательские изменения и включай в коммиты только файлы текущей задачи. Не переписывай чужую историю для устранения конфликтов; сначала изучай обе стороны и объединяй изменения по смыслу.
